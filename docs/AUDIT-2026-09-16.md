# Аудит CehoProxy: проверенные результаты и открытые риски

Это промежуточный аудит, а не подтверждение полной безопасности или завершённой матрицы ОС.

## Подтверждено и исправлено

- Переход от ручного daemon к системной службе: если пользователь включал автозапуск уже после ручного запуска, `chp restart` останавливал только systemd/Scheduled Task и оставлял старый daemon владельцем панели. Новый служебный процесс затем не мог занять порт. Теперь после остановки службы CLI проверяет PID, посылает штатный сигнал оставшемуся daemon и только после его выхода запускает службу. На Debian воспроизведён точный сценарий: ручной PID сменился, systemd active/enabled, один daemon, NRestarts=0, doctor зелёный; оба выбранных CLI вышли через `185.76.13.167`, системный curl через `5.18.234.14`.
- CLI-инструменты: нативные команды проверены реальным TUN на Debian, Ubuntu 24 и Windows Server; скриптовые команды через `chp wrap` проверены на Debian и Ubuntu. Windows `.cmd`/`.bat` shims канонизируются в одну `.cmd`-обёртку. Полный локальный набор: 369/369.
- Ubuntu 24 полностью установлена и настроена: systemd active/enabled, выбранные нативный и обёрнутый CLI используют UZ-выход, невыбранный curl — прямой RU-выход. После reboot матрица сохранилась, doctor полностью зелёный, временный пароль и установочные файлы удалены.

- Сторож процесса отделён от 30-секундного сетевого probe: проверяет sing-box каждую секунду, оба фоновых цикла журналируют необработанные исключения. На Debian после SIGKILL код 137 замечен примерно за секунду, новый процесс запущен ещё через две секунды, вместо прежней задержки более двух минут. Полного fail-closed это не даёт: прямой выход возможен около трёх секунд.
- Debian проверен вторым приложением: `/opt/ceho-python-probe/python3` вышел через 185.76.13.167, системный `/usr/bin/python3` через 5.18.234.14. Doctor: 2 приложения, 1 подписка, все проверки ok.
- Ubuntu 24 VM после первоначального VERR_NO_PAGE_MEMORY установлена с 2 GiB/2 CPU/32 MiB VRAM и настроена для проверки CehoProxy по SSH-ключу.

- Web UI проверен в реальном Chromium при desktop и 375x812: страница не имеет горизонтального overflow, широкая таблица прокручивается внутри `.scroll`. Исправлены отсутствующая программная подпись ручного пути, touch targets вкладок 35.7 px → 44 px и отдельные inline-цвета/рамки карточки ping, которые расходились с dark theme. Detector после первого прохода указал два боковых бордюра и width transition; бордюры устранены, переход ширины оставлен как изолированный внутри полосы фиксированной высоты. Полный набор 351/351.
- Windows Server, реальный стандартный пользователь с Medium Integrity: секреты не читаются, каталог и бинарник не изменяются, панель/status доступны; выбранный curl через 185.76.13.167, системный через 5.18.234.14. Выключение через панель перевело оба выхода на прямой, повторное включение восстановило разделение без UAC. Временный пользователь, ключ и SSH override удалены; задача снова Running от SYSTEM.
- Исправленный Debian после SIGKILL заметил код 137 в пределах 30-секундного цикла и восстановил прокси без двухминутного ожидания Mutex. Штатный `systemctl restart` завершился сразу, Result=success. При падении и начальном старте выбранное приложение всё ещё временно выходит напрямую — fail-closed не реализован.
- Windows 11 загружается до штатного экрана входа. NAT-порт 2223 принимает TCP, но OpenSSH не выдаёт banner; Guest Additions отсутствуют, поэтому Guest Control недоступен. Для продолжения нужен интерактивный вход администратора или отдельное явное разрешение использовать сохранённый лабораторный пароль через виртуальную клавиатуру.

- Windows Server: Users имел чтение config.json/singbox.json и создание файлов в каталоге клиента. Новый клиент применил защищённые ACL: каталог Users RX, секреты только SYSTEM/Administrators; панель продолжила отвечать HTTP 200. Unix singbox.json включён в 0600, регрессия сначала воспроизвела доступ и затем прошла.
- EngineMutex: захват перед await и освобождение другим потоком оставляли Mutex занятым. Регрессионный тест сначала упал. Владение перенесено на отдельный поток; таймаут теперь отклоняет операцию вместо продолжения без очереди. Полный набор 351/351. Старый Debian после SIGKILL движка восстановился только спустя более двух минут, выбранное приложение в это время вышло напрямую. Повторная проверка исправленного клиента выполняется.
- Debian обычный пользователь без sudo: выбранный curl через прокси, системный напрямую, панель HTTP 200. Пользователь удалён после теста.

- Обновление Unix в пути с пробелами теряло executable bit: тест сначала воспроизвёл отказ, File.SetUnixFileMode сохраняет 0755. Старый клиент остаётся в .old.
- Сбой финального перемещения обновления: при отсутствии target и наличии backup исходный клиент возвращается. Тест с отсутствующим скачанным файлом проверяет настоящий путь замены и восстановление original.
- Server: корректный Get-LocalGroupMember по SID Administrators подтвердил, что в группе только Administrator; CehoProbe не является её членом. Выполнение приложений от CehoProbe всё ещё не подтверждено.
- Debian после пяти рестартов остаётся active, свежий warning-журнал пуст.

- Управляющий HTTP: реальный POST /api с Origin чужого сайта выполнялся без пароля. Проверка Origin/Referer/Sec-Fetch-Site добавлена перед маршрутизацией; также закрыт внешний GET /apps/pick. Пять HTTP-регрессий проверяют 403 для чужого источника и 200 для локального CLI и same-origin. Добавлен запрет встраивания панели во frame.
- Чистая Debian: при отсутствии config.json и наличии panel.port ConfigUnreadable ошибочно запрещал запуск daemon даже root. Исправлена ветка отсутствующего файла для повышенного процесса. На VM подтверждены пять рестартов с HTTP 200, Result=success и NRestarts=0; это тест панели без активного туннеля.
- Временный пользователь Debian cehoauditplain (без sudo, только собственная группа) успешно вызвал version и получил панель HTTP 200; бинарник недоступен на запись. Учётная запись удалена после теста.
- Windows: временная задача S4U для CehoProbe не зарегистрировалась (HRESULT 0x80070005). Запуск под ним по-прежнему не подтверждён; наличие административного токена само по себе не объясняет отказ планировщика.

- Unix: `Auth.RestrictConfigAccess` передавал пути в chmod без кавычек. Для каталога с пробелами конфигурация и кеш подписки оставались читаемыми другими пользователями. Регрессионный тест воспроизвёл OtherRead; File.SetUnixFileMode исправил результат на 0600.
- Обновление: Updater принимал файл больше 1 МБ, даже когда его размер не совпадал с размером release asset. Тест с ответом 2 МБ вместо 4 МБ воспроизвёл замену клиента. Теперь обновление отклоняется, .new удаляется, исходный клиент остаётся на месте.
- Windows PowerShell 5.1: локализованный install.ps1 без BOM ошибочно декодировался при запуске через -File. BOM восстановлен. Установщик реально выполнен на Windows Server, скачал клиент с GitHub и установил 1.2.51.

## Исправления прежних выводов

- SSH Administrator на Server VM имеет повышенный токен: IsInRole(Administrator) вернул True. Недостаток UAC-прав не был доказан причиной прежнего Access is denied.
- Invoke-Expression поддерживает param: проверено на VM вызовом, вернувшим 123. Прежнее объяснение удаления param неверно.
- Удаление WaitForExit ранее прошло unit-тесты, но устранение systemd timeout под активным туннелем не подтверждено повторным воспроизведением. Нельзя считать Linux стресс завершённым.
- Создание CehoProbe само по себе не подтверждает успешный запуск приложений под обычным пользователем. Предыдущая net localgroup проверка завершилась синтаксической ошибкой и не доказывает состав групп.

## Оставшийся блокер

Windows 11 требует восстановления интерактивного административного сеанса, после чего остаётся повторить уже готовую матрицу: установка с GitHub, администратор и обычный пользователь, нативный CLI, `.cmd`-обёртка, прямой процесс, reboot и зелёный doctor.

Дополнительная живая проверка: активный Debian-туннель выдержал три последовательных рестарта службы и перезагрузку VM. После восстановления выбранный curl использует прокси, системный — прямой выход. Во время начального запуска выбранное приложение успело выйти напрямую: стартовое окно требует отдельного решения. В журнале наблюдался stream failed: aborted, полностью чистый журнал не заявляется. Windows Server восстановил туннель после перезагрузки через SYSTEM AtStartup без входа пользователя; выбранный и системный curl сохраняют раздельную маршрутизацию. Полный локальный тест после последних исправлений обновления: 349/349. Windows 11 и полноценная матрица обычных пользователей ещё открыты.

Полный локальный dotnet test: 342/342. Два новых теста сначала воспроизвели дефекты и затем прошли. Существуют четыре nullable warnings в AppTunnelTests.

Windows Server: восстановлена установка клиента 1.2.51, но туннель после удаления конфигурации ещё требует настройки. Windows 11 и полный тест разных пользователей остаются незавершёнными. Тесты существующей рабочей сети mini не проводились.
